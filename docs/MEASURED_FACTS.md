> ### 已撤回的说法
>
> - “问题只是算法障碍。”**已撤回。**证据否定的是当前 hard-assignment + native-FDG 循环中的特定方法，不是否定非线性求解器这一类。

## F13a——无 gauge 的 splice 评估工具是最清晰的证据

`test_res/007-…-chr1`。oracle 的两条拟合轨迹经过 Procrustes 叠加后，在片段层面拼接并直接评分——不重新标记接触，也不重新拟合，因此**完全没有 gauge 非对称**：

## F14——native FDG 拟合对 seed 是确定性的

在同一个 pairs 文件上运行 `hickit -s 1`、`-s 7` 和 `-s 13` 会产生**逐字节相同**的 `.3dg` 输出（三者的 chr1 oracle 拆分 md5 都是 `8e61cfc0c176e712c64bd024b43935c3`）。因此引擎 seed **不能**作为独立拟合对照；拟合间变化的唯一可用来源是数据。Stage 1 的 independent-oracle 对照改用定相训练记录的两个互不重叠随机半集。

整条流水线也能端到端复现：运行 004/005/006 与 007/008/009 是相同配置的两次独立执行，且 `results.json` 中的**每一个数字都逐字节相同**，只有 `runtime_sec` 和 splice 区块派生的行例外（两次运行之间的修复只改变了这一项）。

## F15——双拷贝 FDG 拟合存在标签规范不对称

`copyA`/`copyB` 是规范标签，但引擎**没有**对称处理它们。翻转每条接触的标签（`gauge_all`，纯规范变化）会使 chr1 held-out rho 从 **0.6389 变为 0.6169**，不对称为 **0.0220**——与 20 Mb 交换效应同量级。chrX 为 0.0207；在 chrX 深度的 chr1 上为 **0.0357**。数据越稀疏，不对称越大，这符合拟合间摆动而非指标伪影的预期（在单个文件内，预测器 `d_a^-a + d_b^-a` 对轨迹顺序严格对称，且已独立核验）。

这是一个后果，也是协议要求：**任何双拷贝比较都必须按规范不变方式进行**（AGENTS.md 更正协议 5）。Stage 1 报告某个翻转 pattern 及其标签互补的均值，参考层同样取 `oracle` 和 `gauge_all` 的均值。`rewire` flip rule 按构造就是互补不变的；9 个 `relabel` pattern 的实测自身 gauge 不对称为 0.0002–0.0186。

## F18——边界松弛不能修复交换

每个候选预算相同：在九条名义 20 Mb 网格线周围 ±2 bins 的范围内进行一轮 hard E-step，然后重新拟合。oracle 结构在该带上的 E-step sign assertion 与真实标签一致，chr1 为 **0.7305**（规则 5 的下限为 0.55）。每个整片段交换候选仍低于松弛后的 oracle，因此差异不是片段边界处硬切造成的伪影。

该预算有一个限制，运行 README 已明确说明：带状区域位于 20 Mb 网格上，因此能准确覆盖完整片段墙，但**漏掉 5 Mb 和 10 Mb 墙**。

### 仅有深度并不能解释

在同一染色体、其他条件相同的情况下，按定相训练深度变化的效应量（chr1，`--ph-subsample`）：

| 定相训练记录数 | 汇总规范不变 delta，5 Mb | splice delta，5 Mb | splice delta，20 Mb |
| ---: | ---: | ---: | ---: |
| 16,928 (full) | +0.0107 [−0.0036, +0.0264] | +0.0151 [+0.0055, +0.0257] | +0.0314 [+0.0152, +0.0478] |
| 14,000 | +0.0263 [+0.0138, +0.0397] | +0.0128 [+0.0028, +0.0243] | +0.0274 [+0.0108, +0.0452] |
| 11,000 | +0.0280 [+0.0144, +0.0415] | +0.0168 [+0.0087, +0.0256] | +0.0352 [+0.0182, +0.0532] |
| 8,000 | +0.0087 [−0.0066, +0.0257] | +0.0137 [+0.0057, +0.0229] | +0.0244 [+0.0076, +0.0426] |
| 5,209 | +0.0100 [−0.0073, +0.0279] | +0.0123 [+0.0052, +0.0207] | +0.0153 [+0.0017, +0.0287] |
| **chrX (5,209)** | +0.0047 [−0.0195, +0.0293] | **−0.0041 [−0.0166, +0.0080]** | **+0.0054 [−0.0106, +0.0223]** |

**chr1 的 splice 评估工具几乎不随深度变化**：从 16,928 降到 5,209 的每个深度都能检测到 5 Mb 墙。但在**同样** 5,209 条定相训练记录下，chrX 在 60 Mb 以下都检测不到。因此深度不是解释。

测得的其他差异：

- oracle 自身的留出 rho：chr1 全深度 **0.6389**、chr1@5209 **0.5451**、chrX **0.4525**。
  chrX 的拟合结构起初就是更差的预测器，因此交换在更嘈杂的基线上只形成更小的扰动；
- chrX 的 168 个 bin 中有 10 个**没有**定相训练接触（chr1：0），因此 FDG 主链存在空洞；这也是 chrX 候选丢掉 16% 留出区间对的原因；
- chrX 有 1,059 个留出区间对，而 chr1 有 1,622 个，使每个 CI 放宽约 1.25 倍；
- chrX 的两份拷贝并**不更相似**：两条染色体的拷贝间距离矩阵 rho 都是 0.171，平均 `|dA−dB|/dbar` 为 0.470 对 0.476。因此*信号*可比，但*测量*不可比。

### 后果

支持的片段尺度是（定相深度 × 覆盖均匀性 × 留出配对数）的函数，**不是深度单独的函数，也不是染色体单独的函数**。chr1 和 chrX 是该轴的两个端点，不是单纯的深度对比。任何逐染色体结论旁边都必须给出这三个数字。

### 该结果暴露的方法学缺陷

预注册决策规则用 `max(null spread, engine gauge asymmetry)` 对 delta 设阈值。该阈值本身只是一次有噪声的抽样：在深度扫描中为 0.0092–0.0357。在 11,000 和 14,000 条定相记录时，阈值后的“检测限”读成 5 Mb，优于全数据运行的 20 Mb，纯粹因为规范不对称碰巧较小。**该规则适合一次预注册比较，但不适合作为检测限曲线的估计量。**对于曲线，应报告带 CI 的效应量，而不是阈值化的标志。

## F19——拟合噪声地板与最小检测效应同量级

`test_res/007-…-chr1`。两个互不重叠的半数据 oracle 重拟合（标签相同，每个含 8,464 条记录）相对全数据 oracle 的 delta 为 +0.0520 [+0.0271, +0.0782] 和 +0.0100 [−0.0085, +0.0296]。因此改变训练数据量最多会使分数移动 **+0.052**，大于 20 Mb 交换效应（+0.024）。这是 Stage 1 结论的限制，不是零假设：它是不同候选，而不是同一候选的重新标记。这也是受影响配对读数和无规范的 splice 支撑结论的原因；20 Mb 汇总结果必须始终带 CI，绝不能只写裸差值。

## F22——染色体间接触对于放置是必要的，但会降低 cis 准确率

## F10——hard EM 的吸引域半径（第 1 步结果）

评估工具：`contrast` = mean(rho(dA,dA*), rho(dB,dB*)) − mean(rho(dA,dB*), rho(dB,dA*))，其中 (dA*, dB*) 是在训练折上对真实拆分拟合的结构。0 = 塌缩，**0.1993 = chr1 的精确真值**。脚本：`docs/exploration/basin_radius4.py`。

将真实拆分污染 f 比例的接触，运行 6 轮 hard EM、2 个 seed：

| f | 初始 contrast | 最终 contrast（k=6） | 真值百分比 |
| ---: | ---: | ---: | ---: |
| 0.00 | 0.199 | 0.189 | 95% |
| 0.20 | 0.116 | 0.163 | 82% |
| 0.35 | 0.065 | 0.129 | 65% |
| 0.40 | 0.040 | 0.093 | 47% |
| 0.44 | 0.025 | 0.049 | 25% |
| 0.48 | 0.012 | 0.017 | 9% |
| 0.50 | 0.005 | ~0.00 | 0% |

结论：

1. **真值是稳定驻点**，塌缩也是稳定驻点。至少存在两个吸引子。
2. **没有悬崖。**恢复程度随初始污染平滑变化；一轮 EM 大致使 contrast 翻倍，然后进入平台。EM 放大弱信号，而不是摧毁它。
3. **只能使用 hard E-step。**随机/soft 变体在两轮内把真值从 0.199 压到 0.015（采样噪声）。native FDG 没有分数计数输入，因此无法进行适当的 soft M-step。
4. **起点目标：contrast >= 0.10**，对应真值的至少 65%。随机起点为 0.005。没有需要跨过的阈值，只有需要爬升的梯度——因此项目的全部难点在于构造 contrast 约 0.1 或更高的起点。

| `corr(S u_true, delta_true)` | 0.197 |

1. **不是小扰动。**`|delta|/dbar = 0.51`，因此 `delta = (u_i-u_j).vhat` 无效。
2. **构造需要精确的 `Z = (X+Y)/2`。**令 `X = Z+u, Y = Z-u`，其中 `Z` 为 FDG 共识且使用**真实** `u`，得到的 matched contrast 为 `-0.007`，因为共识只能达到 `rho(DZ, Dmid) = 0.871`。 sanity check：令 `Z` 为精确中点时，同一构造会逐位复现真值（+0.2665）。

## 指标陷阱——“两份结构有多不同”不等于正确性

`1 - rho(dA, dB)` 会被任何足够大的随机扰动最大化：与真实半差相同幅度的随机场在 t=0.5 时得分 0.71、t=1.0 时得分 0.85，都远高于真值 0.2665。只有相对真实结构的 matched-minus-swapped 形式有效：

```
contrast_matched = mean(rho(dA,DA), rho(dB,DB)) - mean(rho(dA,DB), rho(dB,DA))
truth = +0.2665 ; u = 0 -> 0.000 ; random u -> +0.009
```

第 2.1 步吸引域数字使用了 matched 形式，仍然有效。

## 更正后的错误日志——第一轮可辨识性测试是错误的

在这次侦察中发现并修复了三个符号/定义错误。记录它们，是因为 `AGENTS.md` 现有规则 7 用来防止重犯。

(a) **标签不完整的 oracle。**第一版可辨识性测试（`docs/exploration/id_test.py`）报告 `oracle − random = +0.0024`，即没有信号，并一度暗示问题不可辨识。这是伪影：它使用了任何 phase 状态的接触，并用 `k % 2` 将其中 68% 未定相接触分配给拷贝，因此“oracle”只由部分标签驱动，两个候选结构都被拖向共识。限制到完全定相接触（F9 协议）后，答案从 +0.002 变为 +0.043。

同一 bug 也影响了本文件此前记录的泄漏数字（共识 0.670、oracle 0.703、random 0.685）。这些数字已由 F9 取代。规则是：oracle 只能由标签完整的接触构建，在训练折上拟合，在测试折上评分。

(b) **soft E-step 方向反了。**`basin_radius2.py` 使用 `P(copy A) = dA/(dA+dB)`，而混合权重实际是 `dA^-a/(dA^-a + dB^-a)`——该分配与真值反相关。soft 模式结果作废。

(c) **sanity comparison 方向反了。**`basin_radius3.py` 分配本身正确，却把 `(sc > 0)`（A 更近）与“0 表示 copy A”的标签比较。它报告 0.34，而正确答案是 0.66，sanity assertion 被触发。现已修复；该断言永久保留。

第 4 个陷阱是概念问题而非 bug：第一次吸引域测量使用逐接触一致率作为评估工具。E-step 对每个区间对只做**一个决定**，因此即使结构完美，一致率也被上限 E[max(pi, 1−pi)] ≈ 0.60–0.70 限制。一轮从 1.00 降到 0.61 意味着“触及上限”，而不是“塌缩”。结构层面的 `contrast` 才是正确评估工具。

## 观测量对拆分是偶函数——符号是相位变量

写出共识 `Z` 和半差 `u = (X − Y)/2`。对于共识分离为 `dbar`、单位向量为 `vhat` 的区间对：

```
delta_ij = (u_i - u_j) . vhat_ij ,  d_A = dbar + delta ,  d_B = dbar - delta
lambda_A + lambda_B ~ 2 c dbar^-a [ 1 + (a(a+1)/2) (delta/dbar)^2 + O(delta^4) ]
```

计数只通过 `delta^2` 依赖拆分。`delta` 的*符号*——即单倍型分配——不在数据中。它必须通过全局要求恢复：符号模式必须能作为一个 3N 维场 `u` 的 `delta = M u` 实现。在 chr1 上，约有 5,000 个可用区间对，而未知量为 3N ≈ 580（过采样约 9 倍），因此模式通常能被确定——除了平凡的 `u = 0`。

这同时解释了已观察到的两个陷阱：

- `u = 0`（塌缩）近似复现观测总和，因此是任何局部方法的驻点——F6。
- 随机起点随机分配符号；随后两份拷贝都看到同一混合的无偏半份，并松弛到同一个共识，因此起点**本身就是驻点**。

**打破对称性是相位恢复问题，而不是逃离鞍点问题。**刚性的拷贝平移无济于事：它不改变拷贝内距离，因此也不改变 `delta`。

## 不存在分子层面的连接信息

如果接触可以按分子分组，从无标签接触中恢复单倍型会很容易
（类似 linked-read：同一个分子上的所有连接共享一个拷贝），问题就会变成秩 2 分解。**这里不存在这样的分组：**

- `readID` 在 `data/P9016.pairs.gz` 的每一行都是 `.`；hickit 的 `hk_print_pair` 无条件写入 `.`，因此 hickit pairs 从不携带 read ID。
- CHARM 原始文件（`/shared/zliu/CHARM/CHARM_mesc/data/pairs/P9016.pairs.gz`，md5
  `5924b9c4f75f04cc725ec7172e3d997f`，与工作区副本相同）和旧备份
 （`pairs_bak/`，md5 `11966ea09b69e51e3e21fc5bd616755d`）也都使用 `.`。
- 在 `/shared/zliu/CHARM/` 下没有找到 P9016 的 `.seg` 文件。
- 文件按位置排序，因此行之间的相邻关系不携带分子信息（只有 2.83% 的连续行共享一个端点，与排序数据一致）。

如果以后找到 `.seg` 文件，或找到带 read 名称的未约简 pairs 文件，就会定性改变该项目的难度，应优先重新评估。

## 原生引擎

`native/hickit/` 是 `/work/phase3/hickit/` 中 FDG 实现的逐字节相同副本（CPU 构建，`make hickit`，无 CUDA）。已核验：随仓库提供的二进制在 chr1 oracle 数字上与 phase3 二进制精确到小数点后四位（0.5894 / 0.5719）。哈希见 `native/hickit/PROVENANCE.md`。
